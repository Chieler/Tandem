# cntctr 0.4.0: the hook channel

Date: 2026-11-12. Status: draft 4, after two adversarial reviews (review-spec-0.4.0.md, review-spec-2.md) and one check of draft 3 (review-spec-3.md: one blocking finding, answered in H3 "A wake that no hook answers" and U11b). Base: 0.3.0.
Inputs, all in .worktrees/_audit/: research-hooks.md (documentation and binaries, nothing run), research-tmux.md (experiments on tmux 3.7c), spike-hooks-agy.md, spike-hooks-claude.md, spike-hooks-codex.md (real sessions), the two reviews.

## Goal

Until 0.3.0 cntctr works on an agent from outside: it types into the agent's terminal and reads the agent's state from its screen. Both are guesses. Claude Code and agy run user commands at fixed points of a session (hooks), and both were measured. 0.4.0 uses hooks as the first channel for these two harnesses and keeps tmux typing as the fallback. Codex stays on the 0.3.0 path in this release (H0). Every decision is judged against four failures:

- **loss**: text that never reaches the agent that needs it.
- **flood**: text an agent did not ask for.
- **wrong tool**: an agent calls the wrong cntctr tool or misses the right one.
- **stall**: an agent stops with work open and nobody who can act learns of it.

Four rules hold for every decision:

1. Without hooks, or when a hook fails, cntctr behaves exactly like 0.3.0.
2. A hook never blocks a tool call, never answers a permission prompt, never makes a turn fail, never types into a pane.
3. A duplicate is better than a loss, within a limit: when cntctr cannot know that an agent saw a text, it shows the text again and says that it may be a repeat, at most three times (H3). After that the text waits on the board and the sender is told.
4. cntctr does not restart an agent by itself. A stall ends with a message to the agent's parent, who decides.

## Decisions

### H0 Codex stays on the 0.3.0 path
No codex hook experiment has run; it needs the user's trust click. In 0.4.0:
- `cntctr hook codex <event>` prints the neutral answer and records nothing.
- `cntctr hooks install codex` refuses and says why.
- A codex agent never "has hooks" (H2), whatever events are on record. It gets full pasted envelopes, screen state and D4/D11 recovery, as in 0.3.0.
- A codex agent gets H1, H7 and H9, which need no hook.
`codex queue` delivery and codex hooks are a later release, after the spike (experiments 1 to 6 and 8, plus: is the hook session id the `queue` thread id). They do not gate 0.4.0.

### H1 Identity given at spawn (wrong tool, loss)
`spawn` starts the agent with `CNTCTR_PANE` and `CNTCTR_TMUX` (the tmux socket path) in its environment, and `CNTCTR_NAME` as a fallback. The server and the hook command take the pane from these before `TMUX_PANE`. The name is read from the pane's `@cntctr_name` as in 0.3.0, so a rename is followed; `CNTCTR_NAME` counts only when the pane option cannot be read. For codex, which filters the environment of MCP servers, `spawn` also passes the variables as per-session MCP environment settings. A server with none of them falls back as in 0.3.0, plus one step for Claude Code: the pane in `~/.claude/sessions/<pid>.json` of its nearest live `claude` ancestor process. Result: `from=` is not needed in agents that cntctr spawned, nor in Claude Code background sessions.

### H2 One hook command (all)
`cntctr hook <harness> <event>` reads the event JSON on stdin and prints the answer in that harness's format. Limits:
- It ends within 2 s by its own alarm; store busy timeout 1 s.
- At most one tmux read (`show -s`, for open tasks), no network call, no typing.
- On any error or timeout it prints the harness's neutral answer and exits 0.
- It is never registered for agy `PreToolUse`.
- Its whole output stays under the harness budget (H3 size), prompt context and Stop reasons alike.

It records for the calling agent one row: tmux socket, pane, harness, harness session id, harness process id (the nearest ancestor of the hook that is the harness binary; the same walk as H1), event, time. A session start in the same pane replaces the row.

An agent **has hooks** when all of these hold: its harness is claude or agy; its pane is alive; the recorded harness process is alive; a prompt event and a Stop event of the recorded session are both on record (one event kind alone proves nothing about the other). Until then, and whenever one of them stops holding, the agent is treated as in 0.3.0.

### H3 Mail by reference (loss, flood)
Addressed text (send, reply, verdict, follow-ups) to an agent that has hooks is stored first; the store keeps the full body while the mail is pending. Each mail has its own id (the post's row id, as in 0.3.0) and a count of presentations.

**Waking an idle agent.** The sender reserves the agent's wake in the store in one statement (succeeds only if no wake is reserved), checks the screen once as 0.3.0 does before typing (limit screens, permission prompts and shells are seen here), and pastes one line, exactly `[cntctr mail id=<id>] body attached; if you see none, call board`. A sender that finds the wake reserved types nothing: its mail goes with the reserved wake. The reservation ends at the agent's next hook event or after 30 s. A one-line paste has no newline to split and nothing to truncate.

**Attaching.** The prompt hook matches that whole line (nothing looser) and attaches every pending mail of the agent, oldest first, up to the size budget; what does not fit follows at the Stop. Each attached mail becomes *staged* in this turn, and its presentation count goes up by one. A mail staged in this turn is not attached again in the same turn (agy calls the hook before every model step).

**Busy agent.** Nothing is typed. The Stop hook presents pending mail at the end of the turn (H5). If the agent is idle and mail is still pending, the 0.3.0 retry thread (D11) wakes it as above.

**Delivered** means one of:
- the agent called `reply` to that mail's id, or `board` returned that mail's body;
- the turn in which the mail was staged ended with a Stop that the harness reports as a normal end.
A Stop after an error or a user cancel, a turn with no Stop at all, and any other cntctr tool call deliver nothing. Staged mail that is not delivered when the agent's next turn starts is pending again and is presented with the prefix `(may be a repeat)`.

**A wake that no hook answers.** If the reservation ends by its 30 s and no hook event of the agent came, the hook is broken or gone: the agent does not have hooks until its next prompt event, and its pending mail takes the 0.3.0 path (full envelope, D11).

**Limit.** A mail is presented at most three times. The count is stored and goes up when cntctr types a pointer line for the mail, and when a hook attaches or carries the mail without a line of its own (it went with another mail's wake, or a Stop presented it). So a wake that nothing answers counts too. After the third presentation the mail is *stalled*: nothing more is typed or attached for it, it stays in the addressee's `board` and unread count (D13), and the sender gets one mail `undelivered after 3 attempts: <id> to <name>`. Stalled is a stored state; a server restart does not reset the count.

**Size.** Claude Code 8 KB, agy 40 KB, for the whole hook output after JSON encoding. A body that does not fit is written in full to a file at presentation time (created fresh each time, D7 permissions; the store, not the file, is the durable copy) and the context holds its first 4 KB, its last 2 KB and the path.

**No hook ran**: the line itself tells the agent to call `board`, which lists its own undelivered mail (D13) and delivers it.

**Agent without hooks**: the full envelope is pasted, as in 0.3.0.

Accepted remainder: a harness that takes a hook's successful output and drops it, in a turn that then ends normally, with an agent that ignores the line's instruction to call `board`. No event shows this. The real-session check (order of work, step 6) looks for it; if it occurs, delivery for that harness needs the `reply`/`board` acknowledgement alone.

### H5 Stop gate (loss, stall)
The Stop hook holds an agent in only two cases, with one message:
- **Mail** (any agent): pending mail exists for it that was not staged in this turn. The message carries the envelopes within the size budget; they become staged.
- **Open task** (spawned workers only): the agent has an open task, given to this pane, that it has not answered with `reply`. The message names the id and the sender, and adds the unread count when board posts are unread: `read the board, then reply`. This is D12 made into a mechanism, at the one moment D12 names: before the final reply.

Never held:
- a second Stop of the same turn (loop guard per harness);
- a second time for the same task id, in any later turn;
- a stop caused by an error or a user cancel;
- an agent without a parent, for board news or tasks: the user's own sessions are held only for mail addressed to them;
- an agent whose open task was given to another pane.

**When a worker gets away.** If a Stop passes for a spawned worker that still has an unanswered task (after its one reminder, or at once on an error), the hook stores one mail for the parent: `<worker> stopped without a reply to task <id> (<reason>)`, once per task. The parent's own server delivers it like any mail. Nothing restarts the worker; the parent sends a follow-up or kills it. A worker that needs input says so with `reply`, which answers the task: there is no separate blocked state.

Board news alone never holds anyone: posts stay pull-only.

### H6 State from events (wrong tool)
For an agent that has hooks, `list` takes state from the last event: prompt submitted or a Stop that cntctr blocked means busy, a Stop that passed means idle, a Claude Code permission event means waiting for permission until the next event. The screen confirms, as in 0.3.0, in these cases:
- a busy or permission state older than 2 minutes (a limit screen or a crash inside a turn shows up here);
- every non-idle state of an agy agent (its events cannot tell permission from busy);
- always before cntctr types into a pane (H3).
The usage-limit state stays screen-based. An agent whose recorded harness process is gone does not have hooks (H2), so a shell left behind by a crashed harness is read from the screen.

### H6b `list` speed (wrong tool)
`list` reads all panes with one `list-panes` call, takes state from events where H6 allows, and reads the screen for the others, one `capture-pane` each. Target, as a check on the development machine and not a guarantee: under 1 s for 32 agents that have hooks and fresh events.

### H7 Paste guard (loss)
Before every paste cntctr reads `#{pane_input_off}` and `#{bracket_paste_flag}`. Input off: the text is undeliverable and takes the D4 path. Bracketed paste off and the text has a newline: cntctr rechecks for up to 2 s (`CNTCTR_PASTE_WAIT_MS`), then takes the D4 path. The check can race with the program; D4 and D11 remain the net below it. tmux is not forked: the measured faults are in how the receiving program takes input, and tmux cannot acknowledge receipt even if changed.

### H9 Model routing (wrong tool)
Independent of the hook channel. Codex: light and standard route to gpt-6.1-terra (low, medium), hard to gpt-6.1-terra high, review to gpt-6.1-sol high. The whole words `adversarial` and `red team` route to review. gpt-6.1-sol is reachable only through the review tier or an explicit `model`; an explicit `model` or `tier` always wins. gpt-6-terra is not in the table: the account refuses it.

### H10 Installing hooks (all)
`cntctr hooks install claude|agy` adds the cntctr entries to that harness's JSON hook file (claude: `~/.claude/settings.json`, events `SessionStart`, `UserPromptSubmit`, `Stop`, `PermissionRequest`, `PostToolUse`; agy: `~/.gemini/config/hooks.json`, events `PreInvocation`, `Stop`), with the absolute path of the running binary, shell-quoted. Rules:
- An entry is cntctr's when its command is `<path ending in /cntctr> hook <harness> <event>` and nothing else. `remove` and a repeated `install` touch only such entries; an entry the user edited into something else is the user's.
- The first install copies the file to `<file>.cntctr-backup`; an existing backup is never overwritten.
- The new content is written to a temporary file and renamed over the old one, and only if the file still has the content that was read; otherwise install stops and says so.
- A file that is not strict JSON is not touched: cntctr prints the entries to add by hand. A missing file is created.
- Every other key and entry is kept; a second install changes nothing.
- No `PreToolUse` entry for agy, ever. `install codex` refuses (H0).
- `cntctr hooks remove claude|agy` takes out the cntctr entries and leaves everything else as it is at that moment. `cntctr hooks status` shows per harness: installed, seen running, binary path and version.

cntctr never installs hooks by itself, never passes a flag that skips hook trust, never answers a trust prompt.

Fixture and fake-process tests cannot show what a model sees; they prove what cntctr stores, types and prints.

## Order of work

One builder at a time, tests first and red inside the step, the whole suite green at the end of each step.

1. H1, H7, H9: three separate small steps, no hook involved (U1, U2, U25 to U27).
2. Store rows for hook sessions and mail states (pending, staged, stalled, presentation count, wake reservation), the event and answer adapters for Claude Code and agy, and the hook command, with delivery still off: U3, U4, U5 and adapter fixtures.
3. `hooks install`, `remove`, `status` (U28).
4. State from events and `list` in one `list-panes` call (U22 to U24).
5. Mail by reference and the Stop gate, together: they share the staged state (U6 to U21).
6. Adversarial review of the whole, then the real-session check on Claude Code and agy: attached context reaches the model; a cancelled turn leaves mail pending; the Stop guards hold; installed files are accepted by the harness.

## Open, needs the user

1. H10 writes to the user's global harness configuration when the user runs `cntctr hooks install`. Alternative: per-project files only. Recommended: global, because agy has no per-session hooks and agents work in many projects.
2. The codex spike needs one trust click in the codex interface. It gates only the later codex release.

## Not in 0.4.0

- Resume after a usage limit (was H8): cut. What a harness does with typed text at a limit screen is unmeasured on all three, a store row plus typing cannot be made exactly-once, and a stale timer can type into a pane that has moved on. `list` shows the limit and its reset time; the parent or the user resumes.
- `codex queue` delivery (was H4) and codex hooks: after the codex spike.
- A fork of tmux: see H7.
- A PTY wrapper around each agent (`cntctr run <harness>`): only if H3 and H7 leave loss.
- Task tracking moved from tmux server options into the store: H2 allows one tmux read instead.
- Claude Code's session socket (`/tmp/cc-socks`): undocumented.
- A human typing in the pane at the moment cntctr pastes: same as 0.3.0.
- Root cause of the lost start of a paste: H3 removes long pastes where hooks exist; log raw pane input if it still happens without hooks.
